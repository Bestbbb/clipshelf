# 多端同步与账号方案

状态：2026-10-31 方案稿。同步代码已存在，但从未在两台真实 Mac 上跑通。

## 1. 现状

CloudKit 私有同步、共享 Pinboard 和托管文件同步的代码已经实现，详见 [托管文件同步协议](SYNC_FILE_ASSETS_PLAN.zh-CN.md)，相关单元测试也已通过。真正的阻塞点不在代码，在发布条件：

- CloudKit 需要一个属于 Apple Developer Program 账号的 iCloud 容器（年费 99 美元），以及签入该容器权限的构建。当前本机开发签名没有这项权限，所以设置页会显示“此构建尚未签署所配置容器的 CloudKit 权限”。
- 给其他人分发、并且启动时不弹安全警告，也需要同一个开发者账号做 Developer ID 签名和公证。

所以第一步是决定是否开通 Apple 开发者账号。开通后，同步和正式分发两件事可以一起解决。

## 2. 三条路线

| 路线 | 账号 | 平台 | 服务器与成本 | 隐私 | 适合时机 |
| --- | --- | --- | --- | --- | --- |
| A. iCloud / CloudKit | 无需 ClipShelf 账号，直接用用户自己的 Apple ID | Apple 设备（Mac，以后可加 iPhone/iPad） | 不需要自建服务器；数据占用户自己的 iCloud 空间；开发者年费 99 美元 | 数据在用户自己的 iCloud 私有库里，开发者看不到 | **第一阶段** |
| B. 自建账号与同步服务 | 需要注册登录（邮箱、Apple、GitHub 等） | 可覆盖 Windows、Android、网页 | 需要服务器、数据库、对象存储和运维，按用户量持续付费 | 必须做端到端加密，否则服务端能看到全部剪贴板 | 确定要做非 Apple 客户端时 |
| C. 局域网直连 | 无 | 同一网络内的设备 | 无服务器 | 不经过云端 | 补充选项，不作为主线 |

## 3. 建议

第一阶段走路线 A。Paste 本身也是靠 iCloud 同步的，这条路不需要账号系统，也不需要服务器，而且大部分代码已经写好。

第二阶段只有在确定要做 Windows 或 Android 客户端时才做路线 B，并且从第一天起就做端到端加密：密钥只保存在用户设备上，服务端只存密文。账号只负责身份和设备管理，不负责解密。

## 4. 第一阶段步骤

1. 开通 Apple Developer Program，创建 iCloud 容器，例如 `iCloud.io.github.bestbbb.clipshelf`。
2. 用 Developer ID 签名，签入 CloudKit 权限，并完成公证。
3. 在 CloudKit Dashboard 部署 schema：`ClipShelfOperationV1`、`ClipShelfSharedOperationV1`、`ClipShelfOwnedFileV1`。
4. 准备两台登录同一 Apple ID 的 Mac，逐项跑下面的验收。
5. 验收通过后再在设置里把同步作为正式功能开放；发布说明写明同步数据存在用户自己的 iCloud 里。

## 5. 双机验收标准

| 场景 | 通过条件 |
| --- | --- |
| 文本、链接、图片 | Mac A 复制后，Mac B 在 10 秒内出现同一条，内容和来源 App 一致 |
| 托管文件 | 64 MiB 以内的文件能完整到达，SHA-256 一致 |
| 删除与编辑 | 一端删除或改名，另一端同步变化，已删除条目不会复活 |
| 离线 | 断网时复制的内容在恢复网络后补齐，顺序正确 |
| 冲突 | 两端同时编辑同一条，结果确定，不丢内容，可看到冲突提示 |
| 换账号 | 切换 Apple ID 后不会把 A 账号的数据传到 B 账号 |
| 共享 Pinboard | 邀请另一个 Apple ID 加入后，成员可见、可撤销，撤销后不再收到更新 |
| 关闭同步 | 关闭后本地历史保持可用，不删除本地数据 |
| 性能 | 1 万条历史首次同步不阻塞面板打开和粘贴 |
