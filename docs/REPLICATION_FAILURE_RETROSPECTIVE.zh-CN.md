# ClipShelf 本次 Paste 复刻失败记录

记录日期：2026-10-10。

**最终结论：本次复刻失败，用户验收未通过，未交付可日常使用的 Paste for Mac 替代品。**

用户在最后一轮修复、安装和自动化测试之后仍明确反馈：“用不了啊 还是不可用的”，并要求将本次过程记录为复刻失败。这是本次交付的最终结论。此前的测试通过记录仅保留为特定条件下的观察，不能抵消实际使用失败，也不能继续作为“已经可用”的依据。

## 1. 原始目标与验收要求

最初讨论跨平台桌面版和多端同步，随后明确优先完整复刻 macOS 版 Paste，免费、开源。用户要求先建立 GitHub 仓库，编写技术 spec 与产品动线文档，并反复强调跨 App 切换的流畅程度。

核心要求是：在正在使用的应用中复制内容 → 唤起历史 → 找到并选择内容 → 回到原应用、原光标位置粘贴 → 继续工作。用户不应为了每轮开发验收反复授权、操作测试文档、清除按键状态或帮助维持前台窗口。

代码、功能清单、编译结果和单元测试均不能代替这一要求。完整对齐还需要界面与动线、格式兼容和日常连续使用的验证。

## 3. 技术事实、证据边界与未解决的问题

已确认的历史缺陷包括：

- 开发签名变化导致辅助功能授权失配。
- 合成按键释放时残留 Command 状态，阻止后续粘贴。
- 搜索后的 Esc 行为与界面提示不一致。
- ClipShelf 已成为前台时，旧捕获逻辑拿不到原目标；失败提示又位于已经关闭的面板中。
- 空分组时的入口不明显，单击选择与实际粘贴动作缺少清晰提示。
- 卡片菜单将 Return 绑定给 Paste，抢占高亮分组子菜单的确认动作。

这些问题有代码变更、日志或定向复现支持。**它们不能被当成用户最后一次“仍不可用”的已确认原因。** 在用户要求记录失败后，没有继续诊断新的失败现场，最终反馈对应的具体入口、焦点状态和触发链仍未定位。不能把它归因于用户操作、权限未开或某个应用不兼容。

曾通过的测试证明的范围有限：

- 内存环境与不显示的测试窗口只能证明部分状态机、布局和回调行为。
- `dispatched` 只表示提交了合成按键，不表示目标应用已经插入内容。
- 读取到目标文档新增内容，可以证明那一次、那个入口、那个目标上的插入，不能推广到全部应用或普通用户的实际入口。
- 从访达打开 ClipShelf 后记录到访达，不是“恢复到文本编辑”的验证。
- 定向发送给 Chrome 的 ⌘⇧V 可能执行 Chrome 自身的纯文本粘贴，不能作为系统全局热键成功的证据。
- 系统全局热键的真实触发、物理键盘前台、全屏/多显示器、富文本/图片/文件完整兼容及长期使用没有完成验收。
- 没有形成足以证明完整 Paste 对齐的原版逐项操作对照；公开资料与局部技术分析不能补齐这一缺口。

## 4. 为什么这次流程失败

1. **核心可用性没有成为扩展功能前的门槛。** 用户最关心唤起、选择、返回、粘贴，开发却在这条流程未稳定时扩展了大量能力。
2. **测试入口与用户入口不一致。** 后台定向输入、工具触发的 reopen、人工准备的光标和合成数据，使部分测试避开了用户实际遇到的焦点与激活问题。
3. **把局部通过提升成了总体交付判断。** 助手反复用构建、签名、测试数量和若干成功插入说明进展，却没有足够证据支持“日常能用”。即使附带未测说明，也不能弥补主结论过早。
4. **诊断与修复缺少稳定闭环。** 先修权限，再修按键，再修目标记录，再发现菜单冲突；已有问题修复后，仍没有证明用户报告的整个失败流程消失。
5. **验证负担过多转移给用户。** 多次要求解锁、刷新授权、操作光标、暂停其他操作、释放 Command，与用户要求自行自动验收的预期相悖。
6. **界面有功能不等于动线可发现。** 分组和粘贴能力存在于代码中，但用户仍找不到入口或无法理解点击后的结果；增加控件后的局部观察也没有换来最终验收。

过程消耗了大量交互与模型调用，用户已明确对成本和耗时不满。本记录没有经过核实的总 token、金额或有效工时，不编造量化数据。结果是这些投入没有换来用户可用的产品。
