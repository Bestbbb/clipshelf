# 应用图标入口的现场诊断与局部修复

日期：2026-10-10。用户再次明确反馈“完全不可用”。**用户验收仍未通过，当前不能作为已验证的日常产品或 Paste 替代品交付。**

用户随后明确主要表现为“选了内容，回不到原 App 粘贴”。本轮只修目标恢复入口与失败反馈。

## 新增现场证据

普通模式追踪 `build/core-flow-rerun/final-diagnostic.jsonl` 记录到 16:18–16:19 三次操作：访达激活 → ClipShelf 激活 → `reopen` → 捕获 `com.apple.finder` → 向访达派发粘贴。对应时段没有全局热键回调。

这确认了应用图标入口会把访达的导航窗口当作接收方。它能够解释部分“选了内容却回不到输入处”的现象，但日志没有剪贴内容、窗口标题或用户意图，不能断言这是所有不可用反馈的唯一原因。

## 本次修改

- 从应用图标打开且来源是访达导航界面时，要求明确选择接收应用，不再自动向该访达窗口粘贴。可选项来自正在运行且有窗口的应用，保留所选应用的窗口和输入焦点快照。
- 面板底部显示目标选择器及“粘贴到应用”按钮。全局快捷键正常唤起时直接捕获原应用，不枚举所有应用，不额外增加选择步骤。访达内的重命名、搜索输入，以及通过快捷键向访达粘贴文件的行为保留。
- 面板关闭后的粘贴失败增加自动消失的浮动提示，不要求点击关闭，不激活 ClipShelf。面板仍开着时继续在面板内显示原因。
- 保留原窗口、原输入位置、剪贴板和修饰键的派发保护。本次没有按猜测放开焦点验证。

## 测试限制与中断

仍是合成系统事件和独立测试窗口，不是物理键盘验收。尚未证明富文本、图片、文件、全屏、多显示器、长期使用或任意应用通过，也未证明用户所有失败都已消除。

Chrome 测试页面最初已关闭，重新打开独立本地页面后完成测试。一次访达入口的早期尝试受前台切换影响，没有实际插入，未计为通过。错误提示测试的一次准备也因前台切换被阻止。新测试工具在每次键盘输入前检查测试文档或 ClipShelf 是否拥有输入上下文，检测到其他应用就停止；这些中断属于测试准备或环境问题，不作为用户故障的原因。

错误提示改用 AX 操作独立测试文档和应用自身控件：先选择文本编辑，再关闭这个已保存的测试窗口，最后执行粘贴。追踪结果为 `copied_only / window_raise_failed`，提示截图已检查。一次测试过早读取按钮标题导致断言失败，改为有上限地等待 AX 状态更新后通过。提示显示后的观察期内通知中心成为前台，因此没有把“整个观察期都保持文本编辑前台”计为通过。

还发现测试工具自身的问题：测试文档不存在时使用 `fatalError`，16:30 的 `native-probe` 和 16:38 的 `panel-probe` 产生了 macOS 崩溃报告。当前测试工具改为打印原因后正常退出。不能将这些工具崩溃算作 ClipShelf 崩溃；测试自身产生的系统干扰也不能归咎于用户。
